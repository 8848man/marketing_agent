### 추후 구현 스펙 — 사용방법을 따라가며 체험하는 튜토리얼

**상태: 설계 초안, 구현 보류.** 앱의 기획과 실제 Mac 게시 흐름이 확정된 뒤 별도 계획·작업·검증을 거쳐 추가한다. 현재 화면에는 튜토리얼 시작 버튼, 코치마크, 진행 저장 기능을 넣지 않는다.

- 목적: 설명을 읽기만 하는 대신 기존 제품 화면에서 ① 영상 불러오기 → ② 영상 선택·초안 확인 → ③ 게시 전 안전 조건 확인을 직접 체험한다.
- 첫 진입에서 `연습 모드`와 실제 모드의 차이를 먼저 설명한다. 연습 단계의 ③은 `DEMO_NO_POST`로 끝나며 YouTube 요청, Chrome 실행, DB 예약, 실제 댓글 게시가 0회임을 항상 표시한다.
- 한 번에 한 행동만 안내한다. 단계 수를 문자로 표시하고 뒤로가기·건너뛰기·다시 시작을 제공한다. 초안이 없거나 RSS가 실패하면 실패 이유와 다음 행동을 보여 주며 막힌 채 종료하지 않는다.
- 실제 모드의 게시 버튼을 튜토리얼이 대신 누르거나 자동 게시하지 않는다. 튜토리얼 완료를 댓글 게시·실제 검증 완료로 간주하지 않는다.
- 새로고침 후 재개와 완료 선호를 저장할 경우 브라우저 로컬의 버전 있는 UX 상태만 사용한다. 세션 토큰·키·초안 본문·계정 정보는 저장하지 않는다. 기존 사용자에게 튜토리얼을 강제 재생하지 않는다.
- 구현 전 결정할 사항: 첫 실행 노출 여부, 데모 진입 경로, 진행 상태 저장 방식, 실제 Mac 화면에서 마지막 단계의 경계, 문구 및 시각 디자인. 이후 수락 시험은 건너뛰기/복귀, 320px·키보드·모션 감소, 데모 외부 호출 0회, 실제 게시 자동 실행 0회를 포함한다.

## R-SETTINGS-UI-01 — 옵션에서 채널 관리 (2026-10-15, 사용자 요청)

**상태: 구현 전에 작성한 명세, Windows 검증 진행 중.** 사용자 정정에 따라 PDF 지정 5개를 기본값과 심사 필수 범위로 유지하되 **5개보다 더 등록할 수 있다**. 등록 범위는 5~20개로 제한해 실수로 너무 많은 순차 RSS 요청을 만들지 않는다. 추가 채널도 사용자가 게시 허용 범위에 포함하라고 명시했다. 그러나 연결 테스트는 소유권 증명이 아니며 게시 전 RSS 소속 재조회·사람 승인 초안·중복/일일 상한 가드를 그대로 적용한다. 벤큐베이터 `SPEC-012-focus-dialog.md`의 포커스·긴 내용 스크롤 원칙을 참고한다.

1. 헤더 우측 상단의 `옵션` 버튼을 누르면 제목이 `채널 관리`인 모달 다이얼로그를 연다. 화면 뒤는 조작할 수 없고, 다이얼로그의 최대 높이는 `min(720px, 85dvh)`다. 제목과 하단 행동은 보이는 위치에 두고 긴 입력 목록만 내부에서 스크롤한다. 좁은 화면에서도 가로 넘침이 없어야 한다.
2. 열 때 로컬 설정의 채널 ID 전체를 읽되 **첫 3개 입력칸만** 보여 준다. `+ 채널 추가`는 아직 숨은 저장값을 순서대로 드러낸 뒤 빈 입력칸을 하나씩 추가한다. 최대 20개에서 버튼을 숨긴다. 숨은 값은 변경·삭제하지 않고 보존한다. `현재 N개 등록 · 3개 표시`처럼 전체와 표시 수를 분명히 알린다. 새 입력칸은 저장 전까지 등록된 것으로 간주하지 않는다.
3. 각 입력에는 순서가 포함된 레이블을 붙인다. ID는 `UC`와 뒤따르는 22개의 영문·숫자·`_`·`-`로만 구성하고 저장할 값은 5~20개이며 서로 달라야 한다. 추가한 빈 칸은 삭제할 수 있다. 저장 시 값 전체를 서버에서 검증한다. 잘못된 입력에는 이유를 표시하고 값을 유지한다. 저장 성공 뒤에는 목록·선택·게시 가능 상태를 초기화하고 다시 영상 불러오기를 안내한다. 저장만으로 YouTube·Chrome·게시 DB 예약은 실행되지 않는다.
4. `닫기`와 Escape는 미저장 입력을 버리고 다이얼로그를 닫는다. 다시 열면 실제 저장된 값을 불러온다. 배경 클릭으로 닫히지 않는다. 열 때 제목에 포커스를 두고 닫을 때 옵션 버튼으로 돌려준다. 기본 키보드 Tab 이동은 다이얼로그 안에 머문다. 모바일에서도 버튼 높이 44px 이상, 모션 감소 설정을 따른다.
5. 실제 모드는 기존 `config.yaml`의 `channels`만 갱신하며 다른 설정과 비밀값을 보존한다. 읽기/저장/연결 테스트 API는 기존 localhost Host·Origin·세션 토큰 경계를 따른다. `--demo`에서는 같은 다이얼로그 구조를 체험할 수 있지만 저장·실제 연결 테스트는 비활성화하고 실제 설정·RSS·Chrome·게시 DB를 읽거나 쓰지 않는다.
6. 기존 YAML 설정 편집 기능은 고급 설정으로 다이얼로그 안에 접어 둔다. 일반 채널 변경은 입력 폼이 우선이다. 고급 편집에서도 기존 검증·비밀 필드 비노출을 유지한다.

### 채널별 연결 테스트

- 각 입력 옆의 `연결 테스트`는 현재 입력값으로 **고정된 YouTube RSS 도메인**에만 요청한다. 리디렉션은 막고 응답 크기·타임아웃을 제한한다. 피드 상단 `yt:channelId`는 입력한 전체 ID 또는 YouTube 실응답처럼 `UC` 접두어가 생략된 값만 허용하고, 각 영상 항목의 `yt:channelId`는 전체 ID와 정확히 일치해야 한다. 다른 값·누락은 실패로 처리한다. 성공 시 `RSS 연결 확인 · 최근 항목 N개`를 해당 행에 표시한다. 최근 항목이 0개여도 연결 성공과 영상 게시 가능 여부를 구분한다.
- 입력 형식 오류·네트워크 오류·타임아웃·RSS 채널 ID 불일치·XML 오류는 해당 행에 한국어로 표시하고 저장값을 바꾸지 않는다. 테스트는 Chrome이나 게시 DB를 열지 않으며 채널 소유권·댓글 가능 여부·초안 승인 여부를 보증하지 않는다.
- 연결 성공 상태는 그 입력값을 바꾸면 즉시 무효가 된다. 저장은 테스트 성공 여부와 무관하게 입력 검증만으로 가능하며, 실제 게시에서는 기존의 게시 직전 재조회가 독립적으로 다시 실행된다.

**수용 기준:** 옵션→열기→3개 표시→`+`로 저장된 4·5번째 값을 표시하고 6번째 이후 새 행을 추가할 수 있다. 5~20개 검증, 다이얼로그 내부 스크롤·닫기·재열기·포커스 복귀가 동작한다. 저장 성공·형식 오류·중복·권한 거부·쓰기 실패에서 데이터와 안내가 일치한다. 숨은 저장값과 다른 설정은 보존된다. 각 행의 연결 성공/실패와 입력 변경 시 결과 초기화를 확인한다. 설정·테스트 요청은 게시 경로를 호출하지 않는다. 데모에는 실제 RSS·설정 변경이 없다.

## R-AI-SETTINGS-01 — 옵션 메뉴와 AI API 관리 (2026-10-15, 사용자 요청)

**상태: 구현 전에 작성한 명세, Windows 검증 진행 중.** 기존 `옵션` 버튼은 첫 클릭에 두 항목이 있는 드롭다운을 연다: `채널 관리`, `AI API 관리`. 항목을 고르면 메뉴를 닫고 해당 모달을 연다. Escape·바깥 클릭으로 메뉴를 닫으며 키보드 초점과 `aria-expanded` 상태를 맞춘다. 채널 관리의 기존 동작은 유지한다.

AI API 관리 모달은 제공사 `GPT (OpenAI)`·`Gemini (Google)`·`Claude (Anthropic)`·`Grok (xAI)` 중 하나와 해당 제공사의 **정확한 모델 ID 문자열**을 설정한다. 제공사별 대표 모델 ID를 드롭다운에 제시하되 모델 목록은 변할 수 있으므로 `직접 입력`도 허용한다. 제공사/모델/키 입력은 현재 활성 구성 하나를 편집하며, 제공사를 바꾸면 이전 제공사의 키를 새 제공사로 재사용하지 않는다. 모델 ID는 빈 값·경로 문자·URL을 거부한다. UI에 쓰이는 모델 표시는 제안값이지 계정 사용 권한의 증명이 아니다.

API 키는 비밀번호 입력칸에서 **쓰기 전용**으로 받는다. 빈 입력으로 같은 제공사의 기존 키를 유지하고, 명시적 `저장된 키 삭제`로만 로컬 키를 지운다. GET 응답·HTML·로그·오류 메시지·초안에는 키를 넣지 않는다. 로컬 Git 제외 `config.yaml`에 저장할 때 기존 원자 쓰기와 소유자 전용 권한을 재사용한다. 환경변수 키를 쓸 수 있다면 상태만 표시하고 값은 반환하지 않는다. 일반 채널/YAML 저장은 AI 구성을 보존해야 한다. `--demo`는 예시 제공사/모델만 보여 주고 저장·연결 테스트·설정 파일 읽기·AI 외부 요청을 하지 않는다.

`연결 테스트`는 **저장된 현재 구성**으로 사용자의 명시적 클릭 때만 해당 제공사의 고정 공식 API 호스트에 최소 JSON 응답 한 건을 요청한다. 요청 URL은 선택한 제공사와 검증된 모델 ID만으로 만들며 임의 호스트·리디렉션은 허용하지 않는다. 타임아웃·응답 크기를 제한한다. 성공은 키와 모델의 이 요청 성공만 뜻하고 댓글 초안 품질이나 게시 승인이 아니다. 키 없음·인증 거부·권한/모델 오류·호출 한도·네트워크·응답 형식 실패를 키/원문 응답을 노출하지 않는 상태로 표시한다. 연결 테스트는 RSS, Chrome, 게시 DB와 분리한다. 요청은 기존 localhost Host·Origin·세션 토큰 경계를 지난 후에만 전송한다.

공통 AI 호출 계약은 `complete_json(system, prompt) -> dict`다. OpenAI, Google, Anthropic, xAI 어댑터가 동일 계약을 구현하고 제공사 선택 팩토리가 활성 어댑터를 반환한다. 기존 Claude 사용 경로와 오프라인 AI는 계속 동작해야 한다. 이 작업은 **연결 구성과 명시적 연결 테스트**까지 포함한다. 선택 영상의 AI 즉석 초안 생성·자동 저장·사람 승인·게시 연결은 별도 B-AI 작업이며 이 설정 저장이나 연결 테스트로 시작되지 않는다.

**수용 기준:** 옵션 메뉴 두 항목과 키보드/닫기 동작, 제공사별 모델 제안 및 직접 ID 입력, 키 비노출·유지·교체·삭제, 제공사 전환 시 키 분리, 새로고침 후 공개 구성 복원, 데모 외부 호출 0회, 거부 HTTP 요청의 AI 호출 0회, 네 제공사 요청/응답의 모의 시험, 연결 성공/오류 상태 표시, 기존 채널 관리·RSS·게시 회귀를 확인한다. 실 제공사 호출은 사용자가 키를 넣고 눌러야 하며, 키나 네트워크가 없는 환경에서는 미검증으로 남긴다.

## B03 — 선택 영상 AI 초안과 사람 승인 (2026-10-15, 사용자 요청)

**상태: 구현 및 Windows 모의 검증.** `DRAFT_MISSING` 영상에서는 사용자가 직접 `AI 초안 만들기`를 눌러야 한다. 이 요청만이 저장된 AI 제공사에 호출을 허용하며, API 키가 없거나 응답이 유효하지 않으면 초안을 저장하지 않고 오류를 보인다. 공통 응답 계약은 `worry_summary`·`cited_detail`·`comment`의 필수 비어 있지 않은 문자열 세 필드이며, OpenAI·xAI는 Responses API의 strict JSON Schema, Gemini는 `responseMimeType: application/json`과 **Gemini Generate Content가 받는 OpenAPI 스키마 부분집합**, Claude는 강제 선택 도구의 `input_schema`로 이 계약을 요청한다. Gemini 요청에는 지원하지 않는 JSON Schema 키를 보내지 않으며 서버는 정확히 이 세 필드를 다시 확인한다. 빈 응답·JSON 형식 실패·스키마 불일치는 서로 다른 한국어 안내를 보이며 원문 응답·키는 노출하지 않는다.

### B03 입력 근거와 사람 검토

1. 새 초안 생성은 먼저 한국어·영어 자막을 가져온다. 자막을 얻지 못하면 RSS 제목·설명을 근거 본문으로 사용한다. 별도 `YOUTUBE_API_KEY` 환경변수가 있을 때만 고정 YouTube Data API에서 공개 인기 댓글의 상위 제한 개수를 읽는다. 키·댓글 조회 실패·댓글 비활성은 초안 생성을 중단시키지 않고, 화면과 저장 레코드에 사용/미사용 근거를 표시한다. AI 키·YouTube 키·원문 오류는 저장·화면·로그에 넣지 않는다.
2. 프롬프트는 실제 근거에서 인용할 구체 문구 한 개 이상, 40~120자, 링크·해시태그·지어낸 운명원 이용 후기 금지, 영상별 다른 문장, 시청자 관점의 자연스러운 운명원·사주 언급을 함께 요구한다. 자막/설명/댓글에 없는 인물·장면·말을 지어내지 말라고 지시한다. 서버는 인용 문구가 사용한 근거 본문에 있는지 다시 확인한다.
3. 키 없는 심사자 환경에서는 제출 시점 다섯 채널 최신 영상의 사람 승인 초안과 그 근거 메타데이터가 `drafts/`에 있어야 한다. AI 키가 없다는 이유로 빈 초안을 정상으로 표시하지 않는다.

1. 생성 결과는 선택한 영상의 ID·채널 ID·현재 제목·근거 텍스트와 함께 영상별 `drafts/<video_id>.json`에 **미승인**으로 저장한다. 기존 초안을 덮어쓰려면 같은 영상에서 다시 명시적으로 생성해야 한다. 생성과 저장은 Chrome 실행·게시 DB 예약·댓글 게시를 호출하지 않는다.
2. 선택 화면은 고민 한 줄·구체 근거·댓글·검토자 이름을 사람이 편집할 수 있게 제공한다. `승인하고 저장`은 영상 ID·채널·제목·근거와 댓글 품질을 서버에서 다시 검사하고 현재 시각·검토자·내용 해시·승인 해시를 기록한다. 승인 뒤에만 게시 버튼을 활성화한다.
3. 사람 검토가 끝나지 않은 생성 초안, 제목·채널·근거 불일치, 40~120자 밖의 댓글, 링크·해시태그·가짜 후기, 브랜드/사주 문맥 또는 구체 근거가 없는 댓글은 게시 불가로 유지한다. 승인 뒤 내용을 바꾸면 다시 승인이 필요하다.
4. `--demo`는 기존 예시 승인 초안만 표시하고 AI 생성·초안 저장·실제 API 호출을 제공하지 않는다. 생성·승인 API는 기존 localhost Host·Origin·세션 토큰 검사를 통과한 POST만 처리하며, 거부 요청에서는 AI 호출·파일 쓰기·DB 예약·Chrome 실행이 모두 0회다.

**수용 기준:** AI 키 없음·AI 응답 오류·생성 성공·미승인·수정 후 재승인·승인 성공을 API와 화면에서 구분한다. 승인된 초안만 기존 게시 가드에 전달되고, 영상 목록 선택만으로 AI 호출·초안 쓰기·게시가 일어나지 않는다. 비정상 요청에서 AI 호출과 초안 파일 변경이 없고, 키는 응답·HTML·초안·로그에 노출되지 않는다.

## R-POST-PROGRESS-01 — 게시 단계와 실패 증거 (2026-10-15, 사용자 요청)

게시 버튼은 별도 클릭에서 기존 RSS·초안 승인·중복·하루 상한을 재검증한 뒤 Playwright persistent context로 이 전용 루트를 연다. 로그인 창이 아직 열려 있거나 로그인이 없으면 게시 전에 실패 코드를 표시한다. 설정 준비 요청은 localhost의 Host·Origin·세션 토큰을 요구하며 영상 탐색·댓글 입력·게시 예약을 하지 않는다. 기본 Chrome 루트 차단은 유지한다. 실제 공개 댓글 클릭은 대상과 문안을 검토한 사용자 승인 후 검증한다.

**수용 기준:** 전용 경로의 생성·기존 경로 재사용·Chrome 없음/시작 실패·잘못된 요청의 무실행을 시험한다. 빈 전용 프로필에서 보이는 persistent context 생성과 앱 화면의 준비 안내를 실측한다. 로그인 상태·한국어 댓글 입력·게시·결과 확인은 실제 계정과 승인된 본인 테스트 영상에서 별도 검증한다.

## R-APP-PROFILE-02 — 로그인 창 점유 안내 (2026-10-16)

앱이 연 전용 Chrome 로그인 창이 계속 실행 중이면 승인 초안을 게시하기 전에 `PROFILE_LOCKED`로 막고, 사용자가 그 창을 정상 종료한 뒤 영상을 다시 선택하도록 안내한다. 프로필 내부 파일이나 다른 Chrome 프로세스는 검사하지 않는다. 로그인 창의 프로세스 상태를 알 수 없거나 종료된 상태에서 Playwright 실행이 실패하면 기존 `BROWSER_LAUNCH_FAILED`를 유지하되 전용 창 종료 후 재시도 안내를 보인다. 차단 시 게시 클릭·예약은 하지 않는다.

**수용 기준:** 앱이 연 창이 살아 있는 동안 프로필 사전 검사와 게시 요청을 차단하고, 종료 후 사전 검사가 풀리는 모의 시험을 통과한다. 전용 루트의 단독 Playwright 실행을 실측한다. 실제 댓글 게시 성공은 별도 확인한다.

## R-YOUTUBE-COMMENTS-01 — 현재 영상 댓글 영역 선택 (2026-10-16)

선택된 YouTube 영상에서 `ytd-comments`가 숨겨진 참여 패널과 표시되는 영상 댓글 영역에 중복 존재할 수 있다. 게시기는 현재 영상의 `ytd-comments#comments`만 스크롤 대상으로 선택한다. 찾지 못하면 `YOUTUBE_NAVIGATION_FAILED`로 게시 클릭 전에 중단하고 화면 캡처를 표시한다. 이미 승인된 영상·문안 외 다른 대상을 탐색하거나 자동 재시도하지 않는다. 현재 댓글 입력창에 작성자 링크가 없으면 YouTube 계정 메뉴의 내 채널 공개 링크를 확인한 뒤 메뉴를 닫는다. 어느 쪽에도 공개 링크가 없으면 게시 전에 작성자 확인 실패로 중단한다.

**수용 기준:** 실제 Chrome의 대상 영상에서 두 요소 중 표시 영역을 확인하고, 중복 요소 상황의 선택자 회귀를 통과한다. 이어서 댓글 입력·게시·확인을 실제 계정에서 검증한다.

수용 기준: 앱 전용 세 프로필의 목록·선택·추가, 선택 표지, 외부 Chrome 프로필 미탐색, 프로필 간 경로 분리, 미설정·잠금·로그인 필요 상태, 명시적 재개, 잘못된/외부 프로필 입력의 HTTP 거부, 댓글 예약 0회 경계를 확인한다. 실제 계정 로그인과 Mac 한국어 YouTube 재개는 별도 실환경 검증으로 남긴다.
## R-APP-PROFILE-04 — 댓글 확인 창 유지와 계정 표시 (2026-10-16, 사용자 요청)

③ 댓글 달기 옆에 기본 꺼짐인 `게시 후 Chrome 창 유지` 토글을 둔다. 켜고 게시가 확인되면 같은 YouTube 댓글 화면과 Chrome 프로세스를 유지한다. 기본 꺼짐에서는 기존처럼 종료한다. 유지 중인 창은 앱이 다음 게시를 위해 강제로 닫지 않는다. 사용자가 창을 닫을 때까지 다음 게시를 `PROFILE_LOCKED`로 차단하며, 이전 게시의 중복·일일 제한도 유지한다. 실패 시 기존 캡처·이유를 남기고 창을 정리한다. ③ 패널의 `앱 전용 프로필 관리` 버튼은 제거하고 옵션 메뉴 및 연결 필요 흐름은 유지한다.

## R-PROFILE-WORKSPACE-01 — 독립 프로필 작업 공간 (2026-10-16, 사용자 변경 결정)

**상태: 명세만 갱신, 코드 미변경.** 앱의 `유튜브1`~`유튜브3`을 각각 안정적인 `profile_id`를 가진 독립 작업 공간으로 다룬다. 프로필 전환 UI는 페르소나·연결·담당 영상·이력을 관리하거나 필터링하는 용도다. 댓글 버튼에서 계정을 고르는 기본 흐름은 두지 않는다. 닉네임과 사용자가 직접 입력한 이메일은 표시용이며 Chrome/Google 로그인 성공의 증거가 아니다. “SaaS 로그인처럼”은 작업 공간의 선택·분리를 뜻하고, 앱 자체가 Google 비밀번호를 받거나 OAuth 토큰·쿠키를 수집하는 로그인 구현을 뜻하지 않는다. 로그인은 해당 앱 전용 Chrome 창에서 사용자가 직접 수행한다.

페르소나·연결 관리 요청은 명시적 `profile_id`에 묶는다. AI 생성·승인·게시의 담당 프로필은 서버가 영상의 **영속 배정 기록**에서 결정한다. 클라이언트가 프로필 ID를 함께 보내더라도 배정과 다르면 거부하며, 화면의 현재 선택 값만으로 게시 계정을 정하지 않는다. 전환 중 진행 중인 작업은 영상에 배정된 프로필에 결과를 기록한다. 프로필 변경은 공유 영상 목록을 지우거나 다시 불러오지 않으며, Chrome 프로필 파일을 앱 코드가 직접 읽지 않는다.

**수용 기준:** 세 프로필의 전환·새로고침·서버 재시작 후 담당 영상과 자료 분리가 일치한다. A 담당 영상의 초안·게시 이력이 B로 옮겨지거나 덮어써지지 않는다. 잘못된/비활성 프로필 ID, 배정과 다른 요청, 동시 전환과 비동기 작업을 시험한다. 프로필 전환만으로 AI·RSS·Chrome·게시 예약은 실행되지 않는다.

## R-VIDEO-CATALOG-01 — 프로필과 독립적인 영상 저장소

`영상 불러오기`는 허용 채널 RSS에서 검증한 영상 메타데이터를 **앱의 공유 영상 카탈로그**에 영상 ID 기준으로 저장·갱신한다. 카탈로그에는 영상 ID, 채널 ID, 제목, 썸네일, 게시 시각, 마지막 확인 시각과 출처를 둔다. 담당 프로필 배정은 별도 저장소에 둔다. 계정 이메일, 페르소나, 초안, 댓글 본문, 게시 상태는 카탈로그에 넣지 않는다. 프로필을 바꿔도 같은 영상 집합·정렬·영상 ID를 보여 주고 재조회는 사용자의 `영상 불러오기` 클릭 때만 한다. 일부 RSS 실패나 프로필 전환은 기존 캐시를 삭제하지 않으며, 마지막 확인 시각과 채널별 오류를 보여 준다. 카탈로그에 있다는 사실이나 배정만으로 게시 자격을 인정하지 않고 게시 직전 소속 RSS 재확인을 유지한다.

제출용 `drafts/latest.json`과 기존 `drafts/<video_id>.json`의 공용 초안은 읽기 전용 템플릿으로 취급한다. 이를 AI 생성 기록으로 자동 표시하지 않는다. 키가 없는 환경에서도 템플릿을 볼 수 있어야 하며, 게시하려면 영상의 담당 프로필 초안으로 명시적으로 가져와 사람이 승인해야 한다.

**수용 기준:** 영상 불러오기 후 A→B→A 전환과 서버 재시작에서 목록과 담당 프로필이 유지되고, 동일 영상이 중복 저장되지 않는다. RSS 일부 실패·제목 갱신·오래된 캐시를 구분한다. 프로필 전환의 네트워크 요청 0회와 카탈로그/배정 기록만으로 게시하지 않는 경계를 시험한다.

## R-PERSONA-01 — 프로필별 AI 페르소나

각 프로필에는 사용자가 편집하는 **AI 페르소나 설정**을 둔다. 표시 이름, 시청자 관점, 말투·어조, 피할 표현을 입력하고 저장한다. 빈 페르소나는 기존 일반 시청자 관점을 사용한다. AI 댓글 생성 요청은 **영상에 미리 배정된 프로필**의 페르소나와 버전을 고정해 공개 영상 근거와 함께 **선택한 AI 제공사에만** 전달한다. 표시용 계정 이메일과 Chrome 로그인 정보는 AI 입력에 포함하지 않는다. 페르소나는 사용자 표현 가이드이며 영상 근거·40~120자·허위 경험/후기 금지·브랜드 및 링크 제한을 덮어쓸 수 없다. 근거에 없는 장면·말·실제 이용 경험을 페르소나로 만들어 내지 않는다.

생성 초안에는 `profile_id`, `video_id`, 사용한 페르소나 버전, 근거와 생성 시각을 남긴다. 페르소나를 수정해도 과거 초안 본문은 조용히 바꾸지 않는다. 현재 버전과 다른 미승인/승인 초안은 `페르소나 변경됨`으로 표시하고, 현재 버전으로 다시 생성하거나 사람이 현재 페르소나에 맞춰 수정·재승인하기 전에는 게시하지 않는다. 생성만으로 사람 승인이 생기지 않는다.

**수용 기준:** A 담당 영상과 B 담당 영상에 서로 다른 페르소나로 생성하며, 같은 영상에 다른 프로필의 AI 초안 생성 요청은 거부한다. AI 요청에는 배정된 프로필의 페르소나와 공개 근거만 포함되고 이메일·키는 노출되지 않는다. 생성 중 화면의 프로필 선택이나 페르소나가 바뀌어도 결과는 시작 당시 배정·버전에 귀속된다. 이전 버전 초안의 자동 게시를 막고, 안전 규칙을 무시하라는 페르소나 문구도 품질 검증을 통과하지 못한다.

## R-PROFILE-VIDEO-STATE-01 — 영상 목록 상태와 색상

공유 영상 카탈로그의 각 카드는 **그 영상에 배정된 프로필**과 작업 상태를 함께 표시한다. 확인된 댓글 게시가 있으면 파란색과 `댓글 게시 완료` 문구를 쓴다. 확인된 게시가 없고 담당 프로필의 AI 생성 초안이 저장돼 있으면 초록색과 `AI 초안 생성` 문구를 쓴다. 둘 다 없으면 기본색과 `미작성`을 쓴다. 파란색이 초록색보다 우선한다. 공용 템플릿만 존재하거나 사람 손으로 작성한 초안만 있을 때는 초록색으로 표시하지 않고 별도 문구로 구분한다. 사람 승인 여부는 초안 상세에서 따로 표시한다.

진행 중 게시와 클릭 후 결과 불명확 상태는 파란색으로 표시하지 않는다. 별도의 `진행 중`/`확인 필요` 문구와 배지를 보여 주고 자동 재게시하지 않는다. 실패는 이유와 캡처를 연결한다. 배정되지 않은 영상은 `담당 프로필 없음`으로 표시하고 초안 생성·게시를 막는다. 색만으로 의미를 전달하지 않고 화면 읽기용 상태 문구를 함께 제공한다. 프로필 관리 화면에서 프로필을 바꾸거나 필터링해도 공유 영상의 상태·메타데이터·순서는 바뀌지 않는다.

**수용 기준:** 서로 다른 세 영상의 담당 프로필이 각각 A/B/C이고 게시 완료·AI 초안만 생성·미작성일 때 카드가 각각 파랑·초록·기본색이다. 승인만 된 공용 템플릿과 결과 불명확한 게시를 각각 별도 상태로 표시한다. 필터 전환·새로고침·재시작 뒤 색/담당 프로필/문구가 일치하며, 키보드·화면 읽기에서 의미를 알 수 있다.

## R-AUTO-ASSIGN-01 — 영상별 프로필 순환 자동 배정 (2026-10-16, 사용자 정정)

**이 결정은 같은 영상에 프로필마다 댓글 1개를 허용한다는 이전 기획을 대체한다.** 영상은 하나의 담당 프로필만 가진다. 사용자는 각 프로필의 페르소나·연결·활성 상태를 관리하고, 댓글 버튼에서 계정을 매번 고르지 않는다. `영상 불러오기`가 검증된 **새** 영상 ID를 공유 카탈로그에 처음 넣을 때, 서버가 담당 프로필을 하나 골라 별도 배정 기록에 원자적으로 저장한다. AI 초안 생성과 사람 승인, 댓글 게시 모두 이 담당 프로필에 묶인다.

후보는 사용자가 `자동 배정 사용`으로 활성화했고 앱 전용 Chrome 프로필 경로가 준비된 프로필이다. 페르소나는 빈 값일 수 있으며 이때 기본 시청자 관점을 사용한다. 표시용 이메일이나 추정 로그인 상태는 후보 판정에 사용하지 않는다. 실제 로그인은 댓글 실행 시 확인한다. 후보가 없으면 영상은 공유 카탈로그에 `담당 프로필 없음`으로 남고 AI 생성·게시를 막는다. 이후 후보가 생기면 미배정 영상만 배정한다.

배정 알고리즘은 `유튜브1 → 유튜브2 → 유튜브3 → 다시 유튜브1` 순서의 **영속 라운드 로빈**이다. 후보 중 활성 프로필 ID를 고정 순서로 정렬하고, 마지막으로 배정한 프로필 다음 후보를 고른다. 한 번의 RSS 불러오기에서 발견한 신규 영상은 `(게시 시각, 영상 ID)` 오름차순으로 처리한다. 카탈로그 삽입·배정·마지막 배정 위치를 한 DB 트랜잭션에 기록해 동시 클릭·재시작에서도 영상별 배정이 하나이고 순서가 재현된다. 기존 영상의 RSS 제목 갱신·재불러오기·프로필 전환은 배정을 바꾸거나 순번을 소모하지 않는다. 프로필을 새로 등록/비활성화하면 **이후 신규·미배정 영상**의 후보 목록에만 반영한다.

담당 프로필이 나중에 비활성화되거나 로그인에 실패해도 이미 생성·승인된 초안이나 게시 대상을 **다른 프로필로 자동 대체하지 않는다.** 로그인 복구 또는 사용자가 명시적으로 `담당 변경`을 선택해야 한다. 담당 변경은 아직 게시 클릭/결과 불명확 이력이 없는 영상에서만 가능하고, 이전 페르소나로 만든 초안의 승인을 무효화해 새 담당 페르소나로 재생성 또는 사람 재검토를 요구한다. 게시 성공·진행·결과 불명확 영상은 담당 변경을 금지한다. 임의의 외부 Chrome 폴더나 프로필은 후보에 넣지 않는다.

**수용 기준:** 세 후보와 새 영상 7개는 1·2·3·1·2·3·1로 배정된다. 비활성 2가 있으면 1·3·1·3이며 후보가 없으면 미배정이다. RSS 순서가 달라도 신규 영상의 정렬·배정이 같고, 재불러오기/동시 요청/재시작은 배정·순번을 바꾸지 않는다. AI 생성은 지정 페르소나만 사용하며 로그인 실패에 자동 계정 교체가 없다. 담당 변경의 허용/금지와 승인 무효화를 시험한다.

## R-PROFILE-POST-01 — 배정된 프로필로 영상당 댓글 하나

게시 예약의 유일성은 **영상 ID 전체에 하나**다. 서버는 영상의 담당 프로필 ID를 배정 기록에서 확인하고 해당 앱 전용 Chrome 루트만 연다. AI 생성·승인·명시적 `댓글 달기`는 모두 같은 배정에 속해야 한다. 화면의 현재 프로필 선택이나 요청 본문의 임의 프로필 ID로 계정을 바꾸지 않는다. 확인 완료·게시 진행 중·결과 불명확 상태에서는 어떤 프로필로도 같은 영상을 재게시하지 않는다. 브라우저 자동화는 앱 전체에서 한 번에 하나만 실행하고 앱 전체 하루 게시 상한 기본 10개를 유지한다. 프로필별 담당 수·게시 수는 정보로 표시한다.

기존 DB의 `video_id` 단독 UNIQUE 게시 기록은 유지한다. 기존 게시 기록에 프로필이 있으면 해당 영상의 담당으로 귀속한다. 프로필을 알 수 없는 과거 게시 기록은 `기존 기록 확인 필요`로 격리하고 자동 재배정·게시하지 않는다. 아직 게시되지 않은 기존 영상은 새 후보 규칙으로 순차 배정할 수 있으나 공용 초안은 AI 생성으로 꾸며 표시하지 않는다. 마이그레이션 전에 앱 데이터 폴더 안에 원본을 백업한다. 쿠키·비밀번호·Chrome 내부 파일은 읽지 않는다.

**수용 기준:** 같은 영상은 A에 배정되면 A의 별도 사람 승인·클릭으로만 게시되고, B의 직접 요청·A/B의 두 번째 클릭은 Chrome 실행 전에 차단된다. 결과 불명확 상태는 재시작 뒤에도 보류된다. 앱 전체 11번째 게시가 차단된다. 이전 DB/초안 마이그레이션은 원본 보존·확정 프로필 귀속·미상 프로필 격리를 검증한다.

## R-PROFILE-EMAIL-VERIFY-01 — 실제 YouTube 계정 이메일 확인 (2026-10-16, 확인 페이지는 H18이 대체)

사용자가 프로필 목록에서 `현재 계정 확인`을 누르면, 앱은 그 앱 전용 Chrome 프로필과 이미 불러와 선택한 허용 영상의 watch URL만 연다. 화면에 보이는 YouTube 계정 메뉴의 **현재 계정 헤더**에서 이메일을 읽어 프로필 이름 옆에 읽기 전용으로 표시한다. 다른 계정 목록, Chrome 프로필 파일, 쿠키·암호·브라우저 저장 정보를 읽지 않는다. 댓글 입력·게시·DB 예약·AI 호출은 일으키지 않는다.

**수용 기준:** 허용 영상·선택 프로필 경계, 메뉴 헤더의 단일 이메일만 채택, 실패 시 기존 확인값 무효화, HTTP 토큰/Origin 검증, 외부 파일·비밀정보·게시 호출 0회, 재시작 시 미확인 상태를 시험한다. 실제 한국어 YouTube DOM은 심사 환경에서 확인한다.

## R-AI-ENV-01 — AI 키를 앱 데이터 .env로 분리 (2026-10-16)

AI API 키는 `config.yaml`에 새로 쓰지 않는다. 앱의 `data/dashboard/.env` 안에 제공사 환경변수 이름별로 보관하고, 파일 권한을 현재 사용자만 읽을 수 있도록 제한한다. 기존 `config.yaml`의 키는 시작 시 원자적으로 이 파일로 옮기고, 쓰기 성공을 확인한 뒤 원본 YAML 키 필드를 제거한다. 실패하면 원본을 지워 키를 잃지 않고 서버 실행을 막아 명시적 오류를 낸다. UI·API 응답·로그에는 키를 보내지 않는다. 파일은 버전 관리에서 제외한다.

## R-PROFILE-LOGIN-WINDOW-01 — 로그인 창의 첫 화면 (2026-10-16)

**수용 기준:** 선택 영상이 있으면 그 watch URL, 없으면 불러온 첫 허용 영상 URL을 사용한다. 목록이 없을 때 UI는 Chrome 실행 없이 안내한다. 임의 영상 ID·허용 외 채널은 HTTP에서 거부하고 프로필 연결과 게시 상태를 바꾸지 않는다.

## R-PROFILE-DIRECT-LOGIN-01 — 앱 전용 Chrome에서 Google 로그인 직접 열기 (2026-10-16, 사용자 정정)

**계획 수용 기준:** 로그인·로그아웃·확인 불가의 서로 다른 판정과 화면 문구, 레이블별 루트 격리, 불확실한 상태의 자동 로그인 0회, 읽기 전용 허용 URL, Chrome 잠금 및 재확인, 한국어 YouTube 화면에서의 실환경 검증을 구현 작업의 관문으로 삼는다. 이 항목은 이번 턴에서 UX 계획이며 제품 구현 완료로 표시하지 않는다.
