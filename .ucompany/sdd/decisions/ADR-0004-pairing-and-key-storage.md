# ADR-0004 — 대시보드 페어링과 Windows 키 저장 (ADR-0002 보완)

> 상태 **제안**. 사용자 확인 후 `accepted`로 바꾼다. 근거: 코드베이스 분석 보고서(2026-10-27) H1·H3, 개선 계획 `improve_plan/` 라운드 2.

## 맥락

- 분석 보고서 H1은 "같은 PC의 다른 프로세스가 사람 없이 생성→승인→게시를 호출할 수 있다"고 지적하고, 메모리 키 기반 HMAC 승인 해시와 게시 직전 nonce를 제안했다.
- [ADR-0002](ADR-0002-local-threat-model.md)는 같은 OS 사용자의 프로세스를 신뢰 경계 안으로 두고(SEC-01 수용), 다른 OS 사용자와 원격 웹사이트를 경계 밖으로 둔다.
- 그런데 `GET /`는 조건 없이 세션 토큰이 담긴 페이지를 돌려준다. 127.0.0.1 포트는 같은 PC의 **다른 OS 사용자**도 접속할 수 있으므로, ADR-0002가 막아야 한다고 정한 공격자가 토큰을 얻을 수 있었다.
- 메모리 키 HMAC은 재시작마다 모든 승인을 무효화한다. 저장소에 커밋된 승인 초안(IMP-23)과 심사 흐름이 깨진다. 같은 사용자 프로세스는 초안 파일과 코드를 직접 바꿀 수 있어 HMAC으로도 막지 못한다.
- `.env`의 `chmod 0o600`은 Windows에서 접근 제어로 동작하지 않는다.

## 결정(제안)

1. **페어링(IMP-31):** 대시보드 페이지는 `/pair?code=<실행마다 새로 만든 코드>`에서 받은 `HttpOnly; SameSite=Strict` 쿠키가 있는 브라우저에만 준다. 코드는 실행 창에 출력되고 브라우저가 자동으로 연다. API의 세션 토큰 검사는 그대로다.
2. **HMAC 승인 해시·게시 nonce는 채택하지 않는다.** ADR-0002의 SEC-01 수용을 유지한다.
3. **Windows 키 저장(IMP-32):** Windows에서는 API 키를 DPAPI로 암호화해 `data/dashboard/secrets.dpapi.json`에 둔다. macOS·Linux는 `.env`(0600)를 유지한다.

## 결과

- 다른 OS 사용자는 페어링 코드 없이 토큰을 얻을 수 없다. 원격 웹사이트 방어(Host·Origin 검사)는 그대로다.
- 같은 OS 사용자 프로세스에 의한 조작은 여전히 수용한 위험이다(ADR-0002).
- 브라우저를 완전히 닫았다가 다시 열면 실행 창의 주소를 다시 열어야 한다.
- Windows 키 파일은 같은 Windows 사용자만 복호화할 수 있어 백업·동기화·다른 PC로의 유출에 안전하다.
