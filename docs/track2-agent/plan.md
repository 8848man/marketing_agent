## 판단 관문 A — 키 없는 채널 확인과 초안 최신성

구현 첫 단계에서 Mac과 동일한 실행 환경으로 다음 두 경로를 시험하고 결과(요청 URL, 응답 구조, 영상 ID·채널 ID 추출 여부, 실패 사례)를 기록한다. 여기서 말하는 확인은 **Chrome 영상 페이지를 열기 전**에 끝나야 한다.

1. 필수 RSS 목록: 고정된 다섯 `channel_id`로 YouTube RSS를 HTTPS로 받아 각 엔트리의 `video_id`·`channel_id`가 요청 채널과 일치하는지 확인한다. 게시 클릭 직전 해당 피드를 다시 받아 선택 영상의 소속을 확인한다. 피드 오류, 엔트리 불일치, 선택 영상 누락은 게시 차단으로 처리한다.
2. RSS 목록 밖 영상 및 직접 URL 가점: **영상 시청 페이지를 HTTP로도 먼저 요청하지 않는** YouTube 제공 메타데이터 경로에서 정규화된 `video_id`와 실제 `channel_id`를 함께 얻을 수 있는지 실측한다. 계정 로그인, API 키, 허용 밖 도메인, 미확인 영상 페이지 요청이 필요하거나 안정적으로 검증되지 않으면 이 경로는 구현 완료로 표시하지 않는다. 이 경우 직접 URL 가점은 비활성화한다. 본인 테스트 영상은 개발자가 대시보드 폴더 안의 설정에 정확한 영상 ID·채널 ID와 소유 확인 기록을 사전 등록한 경우만 허용한다. 실행 중 Studio나 다른 페이지로 소유 증명을 찾으러 가지 않는다.

`drafts/<video_id>.json`은 영상 ID·채널 ID·준비 당시 제목·고민 한 줄·본문·근거·작성 시각·검토 시각·검토자·콘텐츠 해시·승인 해시를 담는다. 콘텐츠 해시는 정규화된 영상/채널 ID·제목·고민·본문·근거의 SHA-256이다. **사람이 검토할 때만** 승인 해시를 현재 콘텐츠 해시로 기록한다. 화면은 RSS에 실제 표시된 영상 ID·채널 ID가 일치하고 콘텐츠 해시와 승인 해시가 같을 때만 게시 버튼을 활성화하며, 선택 당시 승인 해시를 보관한다. 새 영상에 초안이 없거나 제목·본문·해시가 선택 후 바뀌면 검토/재선택을 요구한다. 게시 직전 RSS 재확인과 파일 재읽기를 수행하고, 실패하거나 변경됐으면 **게시하지 않고** 이유를 표시한다. 파일명은 정규화된 YouTube 영상 ID만 허용해 경로 이탈을 막는다. 제출 직전 다섯 채널 각각의 최신 목록과 포함된 초안의 일치를 기록한다.

## 판단 관문 B — Mac Chrome 프로필

PDF의 `유튜브1`은 표시 이름이다. 구현 시 Mac Chrome의 **사용자 데이터 디렉터리**와 그 안의 **프로필 하위 이름**을 별도 설정으로 받는다. `launchPersistentContext`/`--user-data-dir`와 프로필 선택 옵션을 실제 Mac에서 조합해, 기존 로그인 상태를 유지한 보이는 창이 열리는지 확인한다. 심사자 프로필을 복사하거나 쿠키·비밀번호 파일을 앱 코드로 읽지 않는다. Chrome이 이미 같은 프로필을 사용해 잠겼거나 경로/로그인이 확인되지 않으면 프로필 실행을 실패 상태로 표시하고 게시하지 않는다. 다른 프로필로 임의 전환하거나 로그인 정보를 수집하지 않는다. README에는 실제 Mac에서 확인한 설정 예와 잠금 해제 순서를 적는다.

## 댓글 1개·하루 10개를 지키는 상태 전이

기존 DB는 새 스키마로 마이그레이션한다. 한 영상 ID에 대해 모든 프로필을 합쳐 하나의 활성 예약만 허용한다. 게시 클릭마다 DB 트랜잭션 안에서 영상의 `POSTED`/`OUTCOME_UNKNOWN`/진행 중 상태와 하루 할당량을 확인하고 예약한다. 하루 상한은 실행 Mac의 로컬 날짜에 대한 `POSTED` + `OUTCOME_UNKNOWN` + 진행 중 예약을 합쳐 계산한다.

YouTube 게시 버튼을 누르기 **직전**에 Mac 로컬 날짜와 일일 슬롯을 다시 확인한다. 예약 이후 자정이 지나면 새 날짜의 상한을 트랜잭션 안에서 다시 적용한다. 게시 버튼을 누르기 전에 실패한 것이 확인되면 `PRE_SUBMIT_FAILED`로 기록하고 예약·일일 슬롯을 해제한다. 사용자가 문제를 해결한 뒤 다시 직접 클릭할 수 있다. 게시 버튼을 누른 뒤 확인에 실패하면 `OUTCOME_UNKNOWN`으로 보류하고 영상 예약과 게시일 슬롯을 유지한다. 같은 영상의 재시도는 화면에서 실제 댓글 유무를 사람이 확인해 상태를 정리하기 전까지 막는다. `POSTED` 영상은 다른 프로필로도 재게시할 수 없다. 모든 전이·해제·수동 판정은 시간순 기록에 남긴다.

## 로컬 게시 버튼의 요청 경계

서버는 `127.0.0.1`에만 바인딩하고 시작할 때 허용 `Host`와 프로세스별 임의 세션 토큰을 정한다. 상태 변경은 `POST`만 받으며 `GET`·RSS 목록 조회·초안 선택은 게시 예약이나 Chrome 실행을 일으키지 않는다. 게시 요청은 같은 출처의 `Origin`/`Host`와 세션 토큰을 모두 확인하고, CORS를 열지 않는다. 거부된 요청은 Chrome 실행·DB 예약 0회로 기록한다. 서버 쪽에서도 G1, 초안 승인, 중복/상한을 다시 검증하므로 화면 버튼의 비활성화 상태만 신뢰하지 않는다. G3에서 다른 웹 탭의 교차 출처 요청을 막는지 확인한다. 이 방식만으로 악의적인 같은 컴퓨터의 프로세스를 인증하거나 물리적 클릭을 증명할 수 있다고 주장하지 않는다.

## 우선순위와 사용자 흐름

1. **Mac localhost 대시보드**를 시작해 화면에 ① 영상 불러오기·② 영상 선택·③ 댓글 달기를 동시에 보여 준다.
2. 버튼 ①은 고정된 다섯 채널의 YouTube RSS를 가져와 썸네일·제목·채널·날짜 목록을 만든다. 한 채널 실패 시 나머지 채널 목록은 유지하고 실패를 표시한다. 필수 흐름은 API 키 없이 작동한다.
3. 버튼 ②는 선택한 `video_id`의 `drafts/` 초안을 읽어 고민 한 줄·댓글 본문과 길이를 보여 준다. 초안이 없을 때는 **키가 없으면 명시적으로 미준비 표시**한다. 선택만으로 게시하지 않는다. 선택적 AI 키가 있으면 새 초안을 만들 수 있다.
4. 버튼 ③은 승인 초안이지만 프로필이 없으면 게시 대신 연결 다이얼로그를 열고, 저장된 프로필과 다른 게시 가드가 모두 준비됐을 때만 심사자의 직접 클릭으로 게시한다. 옵션의 프로필 관리도 같은 다이얼로그를 연다. 표준 Chrome 사용자 데이터 폴더의 `Default`·`Profile N` 이름만 후보로 보여 주고, 계정·쿠키는 읽지 않는다. 게시 직전 영상·채널·초안·중복·하루 상한을 다시 확인하고 **유튜브1** 지정 프로필을 눈에 보이게 연다.
5. 모든 단계의 시간순 기록을 같은 대시보드에서 본다. 실패 시 이유·캡처를 보존하며 결과 불명확 시 같은 영상에 자동 재게시하지 않는다.

## 안전 경계

- **열 수 있는 YouTube 영상 페이지:** 다섯 채널 소속으로 확인된 영상 또는 등록된 본인 테스트 영상. 목록 UI·API 입력을 신뢰하지 않고 게시 직전에 다시 확인한다. 링크 직접 입력 기능을 추가할 때도 같은 가드를 거친다.
- **브라우저 동작:** 영상 열기·댓글 창·입력·게시·확인만 허용한다. 구독·좋아요·계정 설정 변경 코드는 두지 않는다.
- **파일:** 앱이 직접 여는 설정·초안·로그·캡처는 대시보드 폴더 안에 둔다. PDF는 동시에 지정 프로필 폴더 실행을 요구하므로, 앱 코드의 직접 파일 읽기와 Chrome 자체의 프로필 사용을 구분해 코드 검토에 명시한다. 이 해석이 심사자의 안전 규칙과 맞는지 실환경 검증 전에는 미확인으로 둔다.
- **외부 요청:** YouTube와 선택한 AI 서비스만 사용한다. 분석·오류 전송·CDN 서비스는 쓰지 않는다. AI 키는 선택 설정이며 화면·로그·초안·Git에 넣지 않는다.

## U18~U25 — 공유 영상 카탈로그와 영상별 자동 배정 계획 (2026-10-16, 사용자 정정)

**계획 상태:** 정정된 명세 이후 설계·작업 분해만 갱신, 제품 코드 미변경. 이 계획은 `spec.md`의 `R-PROFILE-WORKSPACE-01`, `R-VIDEO-CATALOG-01`, `R-AUTO-ASSIGN-01`, `R-PERSONA-01`, `R-PROFILE-VIDEO-STATE-01`, `R-PROFILE-POST-01`을 따른다. 이전의 `(profile_id, video_id)`별 중복 허용 계획은 폐기한다.

1. **기존 자료 보호와 버전 경계.** 현재 `processed_videos`/RSS 메모리 목록, `drafts/latest.json`·`drafts/<video_id>.json`, `dashboard_post_reservations`의 `video_id` 단독 UNIQUE, `profile` 문자열과 실제 게시 이력을 먼저 목록화한다. 앱 데이터 폴더 안에서 백업·스키마 버전·중단 후 재시작 절차를 마련한다. 기존 게시의 프로필이 확정되면 해당 영상을 그 프로필에 배정하고, 미상이면 격리한다. 기존 공용 초안은 공유 템플릿으로 남기며 AI 생성으로 꾸미지 않는다. 실패한 마이그레이션은 원본을 보존하고 게시 기능을 닫는다.
2. **데이터 소유권 분리.** 공유 카탈로그는 영상 ID를 기본 키로 메타데이터와 마지막 RSS 확인 시각만 보관한다. 별도의 `video_assignment`는 영상 ID UNIQUE·담당 프로필 ID·배정 시각을 보관한다. 프로필 설정은 안정적인 ID·표시용 닉네임/이메일·활성 여부·페르소나 버전을 보관한다. 초안·승인·진행 작업·게시 결과는 배정된 프로필과 영상에 귀속시키되 게시 예약의 영상 ID 전역 UNIQUE를 유지한다. 전역 게시 일일 상한은 별도 집계로 유지한다.
3. **순환 배정 트랜잭션.** 새 RSS 영상을 `(게시 시각, 영상 ID)` 오름차순으로 처리한다. 후보는 활성 상태이면서 앱 전용 Chrome 경로가 준비된 프로필로 제한하고 고정 ID 순으로 정렬한다. 마지막 배정 프로필의 다음 후보를 선택하며 최초는 유튜브1부터 시작한다. 신규 카탈로그 삽입·담당 배정·커서 갱신을 하나의 원자 트랜잭션으로 실행한다. 후보가 없으면 미배정으로 저장한다. 기존 영상의 갱신은 배정·커서를 바꾸지 않는다. 후보 변경은 신규/미배정 영상에만 적용한다. 한 번의 불러오기나 동시 요청에서도 같은 영상에 배정 하나만 허용한다.
4. **요청 경계.** 프로필 전환/필터는 카탈로그를 재조회하거나 초기화하지 않는다. 초안 생성·승인·게시 요청에서 서버는 영상 ID로 배정을 조회해 담당 프로필을 결정한다. 요청이 임의 프로필 ID를 보내면 배정과 대조하고 다르면 거부한다. Host/Origin·세션 토큰·영상 소속·승인 해시를 다시 확인한다. 진행 중 화면 전환·다중 탭에서도 배정된 프로필에만 결과를 기록한다. Chrome 자동화는 한 번에 하나, 배정된 전용 루트만 사용한다.
5. **페르소나와 초안.** 페르소나는 프로필별 편집 UI와 버전으로 관리한다. AI 요청에는 **담당 프로필**의 버전 스냅샷과 공개 영상 근거를 넣고, 이메일·AI 키·Chrome 내부 정보는 넣지 않는다. 기존 검증·사람 승인 절차를 유지하고 페르소나 버전이 바뀐 초안의 자동 게시를 차단한다. 담당 변경은 게시 시도 전의 명시적 복구 작업으로만 허용하고 이전 승인을 무효화한다.
6. **목록 표현.** 모든 프로필 관리 화면은 동일한 공유 카탈로그를 본다. 카드에 담당 프로필을 표시하고, 확인된 게시가 파랑, 담당 프로필의 AI 생성 초안만 있으면 초록, 둘 다 없으면 기본색이다. 진행/불명확/실패·공용 템플릿·미배정은 색과 별도의 문구·배지로 표시한다. 색상 외 텍스트로도 상태를 읽을 수 있게 한다.
7. **전역 게시 예약 유지.** `video_id` UNIQUE와 앱 전체 하루 10개 상한을 유지한다. 다른 프로필 ID로 같은 영상에 게시하려는 요청은 Chrome 전에 거부한다. 로그인 실패 시 임의의 다음 프로필로 바꾸지 않는다. 결과 불명확 상태는 수동 판정 전 전역 보류한다. 게시 직전 RSS 소속·배정·초안·사람 승인 재검증, 글자별 입력과 본인 댓글 확인은 유지한다.
8. **검증 순서.** 공유 카탈로그 지속성 → 라운드 로빈/동시성/재시작 → 프로필별 페르소나와 담당 초안 → 카드 상태 우선순위 → 전역 예약/마이그레이션 → Mac 한국어 YouTube 실환경 순으로 확인한다. 모의 시험과 실제 게시 증거를 구분한다. 원본 PDF의 영상당 댓글 하나와 같은 안전 경계를 유지한다.
- **개발 중 게시:** 우리 채널 영상에는 게시하지 않는다. 본인 테스트 영상으로만 실게시 동작을 검증한다. 심사자용 실행에서야 우리 채널 영상의 [댓글 달기]를 직접 누를 수 있게 한다.

### 2026-10-15 채널 관리 다이얼로그 계획 (R-SETTINGS-UI-01)

사용자 요청과 뒤이은 정정은 **명세 작성 후 구현** 승인 근거다. 먼저 `spec.md`에 3개 첫 표시, 추가 행, 5~20개 저장, RSS 연결 테스트, 게시 안전 경계를 명세했다. 그다음 이 계획과 `tasks.md`의 U03을 기록하고 UI/API 코드를 바꾼다. 앞으로도 `AGENTS.md`에서 모든 기능·UI·API 변경의 스펙 선행을 명시한다.

1. 헤더의 `옵션` 버튼이 native `<dialog>`를 연다. 제목·하단 버튼은 고정 영역, 채널 행은 `max-height: min(720px,85dvh)` 안에서 스크롤한다. `showModal()`·Escape·닫기·호출 버튼 포커스 복귀를 사용한다. 배경 클릭으로 닫지 않는다. 기존 YAML 편집은 다이얼로그 안의 접힌 고급 영역으로 옮긴다.
2. 실제 모드에는 비밀 없는 채널 ID 목록을 반환/저장하는 별도 로컬 API를 둔다. `DashboardSettings`의 원자 쓰기와 기존 추가 설정 보존 로직을 재사용하되 채널 수를 5~20개로 검증한다. 저장 시 선택/목록 상태를 지우고 다시 불러오기를 안내한다. 데모는 동일한 다이얼로그를 읽기 전용으로 보여 주며 실제 설정·RSS API를 호출하지 않는다.
3. 행별 테스트 API는 입력 ID 형식을 검증한 후 `rss_feed.py`의 고정 YouTube RSS 요청·리디렉션 차단·2MB 크기 제한·10초 타임아웃·채널 ID 파서를 재사용한다. 2026-10-15 실제 5채널 피드에서는 상단 `yt:channelId`가 `UC`를 뺀 값이고 엔트리는 전체 ID다. 파서는 상단에서 두 표현을 허용하되 각 엔트리는 전체 ID와 정확히 비교한다. 응답은 해당 ID와 항목 수만 돌려준다. 테스트는 소유권 증명이나 게시 승인으로 쓰지 않는다. Host·Origin·세션 토큰이 틀린 요청은 fetch·DB·Chrome 호출 전에 거부한다.
4. 저장된 추가 채널은 사용자 요청대로 목록과 게시 허용 범위에 함께 들어간다. 다만 게시 전에 실 RSS 소속 재조회, 사람 승인 초안, 중복·하루 상한, 명시적 클릭을 기존과 동일하게 적용한다. PDF 심사 증거의 기본 5채널은 별도로 유지한다.

## 2026-10-17 H01~H06 개선 구현 계획

5. 제공사 메타데이터와 공통 계약을 분리해 UI·키 설정·호출에 같은 등록 정보를 쓴다. 제공사별 보존 옵션의 차이는 문서화하고 지원하지 않는 기능을 동일하다고 주장하지 않는다.
6. 문서·예시 파일을 현재 코드에 맞게 정리한다. 이전 상태 문서는 이력으로 표시하고 원본 PDF의 외부 경로는 재현 가능한 출처 정보로 교체한다.

각 단계는 단위/HTTP 회귀와 정적 링크·스키마 검사 후 적용한다. 실제 외부 호출·Chrome·댓글 게시 시험은 이번 변경의 자동 확인에 포함하지 않는다.

## 2026-10-17 H07~H08 로컬 HTTP 경계 보완

`/api/youtube-key`를 다른 POST와 같이 본문 파싱 단계에서 정확한 스키마로 검사한다. 거부 시 호출과 파일 쓰기는 0회이며 400 JSON 오류를 반환한다. 캡처는 이름·위치·파일 유형·크기를 검사하고 최대 10 MiB만 읽는다. 크기 제한은 실제 화면 캡처에 여유를 두면서 의도치 않은 거대 파일을 한 요청에서 적재하지 않기 위한 값이다. 토큰 검사와 기존 URL 경계는 유지한다. HTTP 모의 시험에서 잘못된 키 본문, 정상 키 본문, 과대·심볼릭 링크 캡처를 확인한다.

## 2026-10-17 H09~H10 문서 대조 후 공백 보완

초안 생성 응답과 초안 미리보기 계약에 기존에 저장된 `source_text`를 노출한다. 선택한 영상의 근거 원문과 출처 목록은 사람 승인 입력 바로 앞의 접을 수 있는 영역에 텍스트 노드로 표시한다. 원문이 없는 이전 초안은 빈 근거를 사실처럼 채우지 않는다. AI가 반환한 인용 문구와 원문을 사람이 대조할 수 있게 하되 승인 해시·품질 검사·게시 조건은 유지한다.

AI 응답 전송 계약에서 크기를 받지 않는 `read()` 대체 경로를 제거한다. 시험 전송 객체도 길이 제한 인자를 받아야 하며, 비정상 전송 구현은 고정 오류 코드로 거부한다. 실제 HTTP 오류 본문은 읽거나 직렬화하지 않는다. 이 보완은 실제 제공사 정책·실키 연결의 수락을 뜻하지 않는다.
