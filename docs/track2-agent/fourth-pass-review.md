# 4회차 계획 개선과 자기 비판

> 앞선 3회는 `three-pass-review.md`에 기록했다. 이번 회차도 원본 PDF 2~4쪽의 수동 게시·허용 영상·안전 규칙을 기준으로 문서만 수정했다. 앱 동작을 검증했다고 주장하지 않는다.

## 수정 전 비판

1. G1-C의 “공개 YouTube 정보”는 미확인 영상의 **시청 페이지를 HTTP로 먼저 요청하는** 구현으로 해석될 수 있었다. 원본의 허용 영상 페이지 외 접근 금지와 충돌할 수 있다.
2. localhost UI에 [댓글 달기] 버튼이 있어도 게시 API가 다른 웹 탭의 요청을 받으면 심사자의 직접 클릭 조건이 약해진다. 기존 계획에는 바인딩 주소·Host/Origin·토큰·HTTP 메서드 검사가 없었다.
3. 본인 테스트 영상의 “소유 증거”가 모호해 실행 중 Studio 등 다른 페이지를 열거나 파일 경계를 넘는 구현으로 흐를 수 있었다.

## 이번 수정

- `plan.md`, `tasks.md`, `validation-protocol.md`, `checklist.md`의 G1-C에 **미확인 영상 시청 페이지는 HTTP와 Chrome 양쪽 모두에서 선행 접근 금지**를 명시했다. 비영상 페이지 메타데이터로 ID·채널을 검증하는 방법이 실측되지 않으면 직접 URL 가점 B02는 비활성화한다.
- 본인 테스트 영상은 대시보드 폴더 안 설정에 정확한 영상·채널 ID와 사전 소유 확인 기록을 등록하도록 했다. 실행 중 소유 확인을 위해 Studio 페이지를 탐색하지 않는다.
- G3를 추가해 `127.0.0.1` 바인딩, Host/Origin·프로세스별 세션 토큰·POST 전용 게시 API, 거부 요청의 DB 예약·Chrome 실행 0회를 수락 시험으로 정했다. 서버는 화면 상태와 별도로 채널·초안·상한을 재검증한다.

## 수정 후 자기 비판

G1-C는 여전히 **실제로 존재하고 안정적인 비영상 페이지 메타데이터 경로가 확인되지 않았다.** 따라서 RSS 밖 영상과 직접 URL 가점은 구현 가능성이 미정이다. G3는 다른 웹 탭의 우발적/교차 출처 요청을 줄이지만, 같은 컴퓨터의 악의적인 프로세스를 인증하거나 사람의 물리적 클릭을 증명하지 못한다. 그 한계를 `plan.md`에 명시했다. Mac과 실제 네트워크에서 G1-A/B/C·G2·G3를 실행하기 전에는 필수 게시 기능을 완료로 표시하지 않는다.
