# 검토 체크리스트

검토 에이전트는 라운드 diff와 계약서들만 보고 아래를 확인합니다.

## 지적 등급

| 등급 | 기준 | 처리 |
| --- | --- | --- |
| 차단 | 계약서 목표 미달성, 보안 약화, 기존 안전장치 약화, 데이터 손실·중복 게시 가능성, 테스트가 실제로 아무것도 검증하지 않음 | 수정 후 재검토. 라운드 게이트 불통과 |
| 권고 | 가독성, 이름, 중복, 사소한 누락 | 라운드 파일에 기록. 다음 라운드나 별도 작업에서 처리 |

판단이 어려우면 차단으로 분류하고 "확신 없음"으로 표시합니다. 메인이 최종 판정합니다.

## 공통 항목

1. **목표 달성**: 각 계약서의 목표 문장이 diff로 실제 달성되었는가
2. **테스트의 실효성**: 새 테스트가 수정 전 코드에서 실패할 수밖에 없는 내용인가. 항상 통과하는 단언, 목(mock)이 결과를 대신 정하는 구조는 없는가
3. **안전장치 보존**: 예약 상태 머신, 유일 인덱스, RSS 재확인, fail-closed 경로가 그대로인가
4. **오류 처리**: 실패 시 게시가 진행되지 않는 방향(fail-closed)인가. 예외를 삼키는 새 코드가 있는가
5. **비밀 처리**: 키·토큰이 로그·오류 메시지·응답에 노출되지 않는가
6. **범위**: 계약서에 없는 동작 변경이 섞여 있지 않은가

## 라운드별 추가 항목

| 라운드 | 추가 확인 |
| --- | --- |
| 1 | 채널 허용 목록이 설정에서 오고 기본값이 안전한가. 패키징 스크립트가 허용 목록 방식이고 금지 패턴을 놓치지 않는가 |
| 2 | HMAC 키가 디스크·응답·로그에 남지 않는가. 토큰이 HTML·URL에 실리지 않는가. nonce가 1회용이고 만료되는가. 비교에 상수 시간 비교를 쓰는가. 쿨다운 검사가 예약과 같은 트랜잭션 안인가 |
| 3 | 락 밖으로 옮긴 코드가 공유 상태를 읽고 쓰지 않는가(경쟁 조건). `OUTCOME_UNKNOWN` 해소가 사람 확인 없이 일어날 수 없는가 |
| 4 | 공통 HTTP 계층이 기존 4곳의 동작 차이(예외 vs `None`)를 의도대로 통일했는가. 마이그레이션이 기존 DB를 손상하지 않는가 |
| 5 | 분리 후 공개 동작(경로, 응답 형식)이 그대로인가. CSP에서 `unsafe-inline`이 실제로 빠졌는가 |
