# 에스컬레이션과 측정

## 재시도 규칙

| 상황 | 조치 |
| --- | --- |
| 작업 게이트 실패 1회차 | 실패한 게이트 ID, 실패 출력, 수정 지시를 붙여 구현 에이전트 재실행 |
| 같은 작업 2회차 실패 | 계약서를 다시 검토. 모호하거나 틀린 부분이 있으면 계약서를 고친 뒤 재실행 |
| 같은 작업 3회차 실패 | **에스컬레이션**: 메인(Opus)이 직접 구현하고, 원인을 라운드 파일에 기록 |
| 검토 차단 지적 | 해당 작업만 수정 지시로 재실행. 재검토는 수정된 부분과 체크리스트 전체 |
| 게이트 실행 불가 | 판정 보류. 메인이 환경을 고친 뒤 재판정 |
| 계약서로 정할 수 없는 결정 발생 | 작업 보류, 사용자에게 질문 |

## 측정 지표 (라운드마다 기록)

| 지표 | 정의 |
| --- | --- |
| 재작업 횟수 | 작업별 구현 에이전트 실행 횟수 - 1 |
| 에스컬레이션 수 | 메인이 직접 구현한 작업 수 |
| 차단 지적 수 | 검토 1회차의 차단 지적 건수 |
| 메인 재조사량 | 메인이 검증 과정에서 다시 읽은 소스 파일 수 |

## 모델 구성 재평가 기준

1라운드가 끝나면 아래 기준으로 D-003(메인 Opus + 하위 Sonnet)을 재평가합니다.

- 작업당 평균 재작업 횟수가 **2를 넘으면** → 구현도 Opus로 전환을 검토
- 메인 재조사량이 라운드 변경 파일의 **절반을 넘으면** → 하위 에이전트로 얻는 절감이 없으므로 전환을 검토
- 둘 다 아니면 현 구성 유지

전환할 때는 결정 기록에 새 항목을 추가합니다.
