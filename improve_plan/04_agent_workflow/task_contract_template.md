# 작업 계약서 양식

메인이 구현 에이전트에게 넘기는 유일한 지시서입니다. 빈칸 없이 채워야 하며, "적절히", "필요하면" 같은 판단 위임 표현은 쓰지 않습니다.

```markdown
## 작업 RN-TM: <제목>

### 1. 목표
<한두 문장. 무엇이 어떻게 달라져야 하는가>

### 2. 배경과 근거
- 위험 항목: <ID>
- 현재 동작: <파일:함수(대략 줄)> 가 <무엇을> 한다 [코드 확인]

### 3. 저장소와 실행 환경
- 경로: <원격 셸 기준 경로>
- 브랜치: <라운드 브랜치> (이미 체크아웃됨, 전환 금지)
- 테스트 명령: <정확한 명령>

### 4. 먼저 작성할 실패 테스트
| 테스트 이름 | 파일 | 기대 동작 |
| --- | --- | --- |
| test_... | tests/test_....py | <입력> 이면 <결과> |

### 5. 수정 범위
- 수정 허용 파일: <목록> (이 밖의 파일 변경 = 게이트 실패)
- 수정 금지 영역: <파일:함수 또는 패턴>
- 하지 말 것: <구체적으로>

### 6. 구현 지침
1. <단계별, 함수 이름 수준까지>

### 7. 완료 조건
- [ ] 4번 테스트가 수정 전 실패, 수정 후 통과
- [ ] <좁은 테스트 명령> 통과
- [ ] 커밋 1개, 메시지: `<type>(<영역>): <요약> (RN-TM)`

### 8. 보고
report_format.md의 "구현 보고" 양식으로 보고한다.

## 게이트 입력
(JSON 블록. 제목은 반드시 `## 게이트 입력` — round_gate.py가 이 제목을 찾는다)
```

## 작성 시 확인할 것 (메인)

- 함수·파일 이름은 현재 코드에서 확인한 것만 씁니다.
- 수정 허용 파일 목록은 게이트 G3의 입력이 되므로 정확해야 합니다.
- 실패 테스트의 "기대 동작"은 구현 방법이 아니라 관찰 가능한 결과로 씁니다.
- 계약서 하나가 커밋 하나에 대응해야 합니다. 커밋 두 개가 필요하면 작업을 나눕니다.
